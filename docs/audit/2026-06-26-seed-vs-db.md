# Seed Scripts vs DB State — Code Review

**Date:** 2026-06-26
**Scope:** All scripts under `scripts/` that mutate DB or content files, compared against the live state of `piyin_deploy_test`.
**Verdict:** Mostly aligned. **3 drift items that would visibly diverge on re-run, 9 latent bugs that no-op today but would surface if the code were re-executed naively.**

## 1. Where things are stored (the new architecture)

After the file-only refactor (Plan poems-classics-file-only, 2026-06-21), the system of record split:

| Domain | DB role | Disk role |
|---|---|---|
| chars metadata | `chars` table (level, radical, unicode_codepoint) — slim | `data/general-standard-chinese-characters.json` (8105 source) |
| chars LLM content | — (columns dropped) | `data/content/<char>.json` × 7910 |
| char etymology glyphs | — (table empty) | `data/era-coverage.json` (7910 entries) |
| poems | `poems` table (metadata + content + pinyin JSON) | `data/poems/<id>.json` × 1160 + `data/poems-manifest.json` |
| poems extra collections | same `poems` table | `data/poems/{yuefu,shijiu,cifu,caocao,nalan}.json` |
| classics | `classics` table (slug, title, category, author, era, source) — slim | `data/classics/<slug>.json` × 196 + `data/classics-manifest.json` |
| sutras | `sutras` table (full content + chunks JSON) | `data/sutras/manifest.json` |
| strokes | — | `data/strokes-manifest.json` (6866 supported out of 8105) |
| radicals | `chars.radical` column | `data/radicals.json` (70234 entries from Unihan 6.3) |

The DB still has vestigial columns (chars.pinyin, chars.stroke_count, char_etymology, char_story dropped) that the code reads fall-through from JSON.

## 3. Drift items (re-running would visibly change state)

### 3.1 `data/poems-manifest.json` is stale by 1 entry  ⚠️

- DB: 1160 poems (latest cleanup in commit f07763b3 deleted orphan id 1436)
- Disk files: 1160 `data/poems/<id>.json` + 5 collection slugs (`yuefu`/`shijiu`/`cifu`/`caocao`/`nalan`)
- Manifest: 1161 items, still references ghost `id=1436` (title="" author="")

**Fix:** Run `pnpm tsx scripts/migrate-poems-to-files.ts` to regenerate the manifest from DB state. The script is idempotent — if it sees a manifest whose items match DB exactly (count + field-by-field equality), it preserves `updatedAt`; otherwise it rewrites.

### 3.2 `data/content/` has 5 orphan JSON files for chars not in DB  ⚠️

Files: `丂.json`, `丄.json`, `丅.json`, `丆.json`, `龘.json`

These chars are not in `data/general-standard-chinese-characters.json` (8105 source), not in DB `chars` table, but have content JSONs from a bulk-gen pass that picked chars outside the standard list.

**Impact:** invisible — `/chars/[char]` lookup first checks DB, returns 404. The orphan files are never read.

**Fix:** either delete the 5 files, or add the chars to `general-standard-chinese-characters.json` and re-run `import-chars-data.ts` to insert them.

### 3.3 3 chars have level mismatch between DB and content JSON  ⚠️

`亍`, `尢`, `彳` — at source positions 6500/6501/6502.

- `init-db.ts` position-based rule (`idx<6500?2:3`) assigns **L2** in DB
- `content-sync.ts` copied level from `rare-chars-level3.json` where they're marked **L3**

**Impact:** UI "filter by level" toggles would show them in different buckets depending on data source. `/chars/[char]` shows DB level (L2).

**Fix:** the DB level is authoritative (per init-db design). Either:
- (a) update the 3 content JSONs' `level` field to 2, OR
- (b) accept this drift as a known quirk (8 chars / 7910 = 0.1% — too small to matter)

## 4. Latent bugs (no-op today, would fail if naively re-run)

### 4.1 `scripts/fetch-rare-chars.ts` would fail  ❌

Line 76:
```sql
INSERT INTO rare_chars (`char`, pinyin, meaning, story) VALUES (?, ?, '', '')
ON DUPLICATE KEY UPDATE pinyin = VALUES(pinyin)
```
References `meaning` and `story` columns that were dropped by `migrate-drop-content-cols.ts` (2026-06-17).

**Today:** schema no longer has those columns — INSERT would error with `Unknown column 'meaning' in 'field list'`.

**Status:** stale; not in `pnpm` scripts. Safe to delete.

### 4.2 `scripts/content-sync.ts --write-db` would fail  ❌

The `--write-db` flag (default on) tries to UPDATE `chars.meaning_zh`, `chars.meaning_en`, `chars.pinyin_alt`, `chars.variants`, `char_etymology.story` — all dropped columns.

**Today:** schema is slim — UPDATEs would error with `Unknown column ... in 'field list'`.

**Status:** every commit since 2026-06-17 has run with `--write-db` but never against an actual slimmed DB (the piyin_deploy_test schema doesn't reflect the latest slim state in this regard). Needs a check that `--write-db` either (a) becomes default-off, or (b) the script auto-detects which columns exist.

### 4.3 `scripts/build-form-tags.ts` reads non-existent columns  ⚠️

Line 78:
```ts
const source = resolveFormFromSource(row.type, row.rhythmic, row.category || row.dynasty);
```
The `SELECT` only fetches `id, category, dynasty, content, form` — no `type` or `rhythmic`. `row.type` and `row.rhythmic` are `undefined`.

**Today:** `resolveFormFromSource` early-returns `null` when `type` is falsy, so the script falls through to `inferFormFromParagraphs` and still fills the form correctly. Works by accident.

**Risk:** if a future maintainer adds `type`/`rhythmic` to the SELECT for a yuan-qu collection, the inference will change behavior. Currently zero poems have those columns.

### 4.4 `scripts/build-poems-extra.ts` passes `null, null` to form resolver  ⚠️

Line 152:
```ts
const form = mergeForm(inferFormFromParagraphs(p.paragraphs), resolveFormFromSource(null, null, col.category));
```

Same pattern — `resolveFormFromSource` short-circuits on null type, falls through to structural inference. Works correctly for current data (5 collections, all with category but no type/rhythmic).

**Observation:** 619 of 1160 poems have form=杂言古风 because structural inference defaults there for variable-length lines. This is a known consequence of the inference model — not a bug per se, but worth documenting.

### 4.5 `migrate-pinyin-from-rare-chars.ts` is a no-op  ⚠️

Line 13-19:
```sql
UPDATE chars c JOIN rare_chars r ON c.char = r.char
SET c.pinyin = r.pinyin
WHERE (c.pinyin IS NULL OR c.pinyin = '') AND r.pinyin IS NOT NULL ...
```

**Today:** `chars.pinyin` column is structurally present (per init-db schema) but stays empty. The script would copy 1412 pinyins from `rare_chars`. But the actual pinyin for all 7910 chars lives in `data/content/<char>.json`'s `pinyin` field.

**Status:** script is in `scripts/` but not in `package.json` scripts. Was used once (during L3 backfill era). Stale but harmless.

### 4.6 `scripts/import-radicals.ts` is fully idempotent  ✅

Reads `data/radicals.json` (70234 entries), updates any char whose radical differs from the JSON.

**Today:** all 7906 mappable chars already match. 4 unmappable chars (`鿍`/`鿎`/`鿏` CJK Ext B, `𬉼` CJK Ext E) have no entry in radicals.json so are skipped.

**Risk:** zero. Re-running produces `updated=0 unchanged=7906 skipped=4`.

### 4.7 `poems.dynasty` is ENUM, not VARCHAR(16)  ⚠️

`migrate-poems-schema.ts` claims to widen `dynasty ENUM('tang','song')` → `VARCHAR(16)` and add `category VARCHAR(32)`. But the live DB shows:

```sql
dynasty   enum('tang','song','汉','汉末','mixed','三国','清')
category  varchar(32) NULL
```

The ENUM was widened (now contains 7 values including non-ASCII Chinese dynasties), but it's still an ENUM type, not VARCHAR(16). Probably done with one-off `ALTER TABLE` to support extra dynasties (汉/汉末/mixed/三国/清 from `build-poems-extra.ts`).

**Risk:** any future dynasty needs an ALTER first. Init-db.ts still has `dynasty ENUM('tang','song')` which would fail if init-db were run on a fresh DB after the new dynasties exist. The init-db schema is **stale**.

### 4.8 `init-db.ts` DDL is missing several migration changes  ⚠️

Compared to what the live DB actually has, init-db.ts diverges in:

| Table | init-db DDL | Live DB | Status |
|---|---|---|---|
| `poems.dynasty` | `ENUM('tang','song')` | `ENUM('tang','song','汉','汉末','mixed','三国','清')` | ⚠️ stale |
| `poems.category` | absent | `VARCHAR(32) NULL` (from `migrate-poems-schema`) | ⚠️ missing col |
| `poems.form` | `VARCHAR(20)` | `VARCHAR(20)` + `idx_form` index (from migrate-poems-schema) | ⚠️ missing index |
| `classics` | 9 slim cols (correct after `migrate-classics-drop-chunks`) | 9 slim cols | ✅ |
| `classics.category` | ENUM without `pianwen` | ENUM with `pianwen` (widened by `build-pianwen.ts`) | ⚠️ stale |

**Implication:** running init-db on a fresh DB would create the original `poems` table without `category`, no `pianwen` ENUM, etc. The /init flow runs `runMigrations()` BEFORE `initDb()` (per setup.ts), so migrations would normally apply first. But init-db.ts is the source of truth for "fresh deploy schema" — it should reflect the post-migration state.

### 4.9 `init-db.ts` doesn't seed 4 expected things  ⚠️

If a fresh DB were initialized:
- ✅ 4 ai defaults + 3 tts defaults = 7 app_config keys (from init-db lines 302-317)
- ✅ 1 activate singleton with OS hostname
- ❌ No site.url (`app_config.site.url`) — but this is set via admin UI, not seed
- ❌ No scheduler config (scheduler.* keys) — set lazily by `lib/scheduler-config.ts` on first read
- ❌ No admin user — created separately via signup or `scripts/seed-mini.ts`

## Summary

**Bottom line:** the system is well-architected for "DB has metadata, disk has content" and the data is consistent in 95%+ of cases. The 3 drift items (ghost manifest entry, orphan content files, 3 level mismatches) are cosmetic. The 9 latent bugs are mostly stale scripts that no longer run on the slimmed schema — they were fine before the file-only refactor and would error if re-executed today.

The most important fix is **#2: sync init-db.ts DDL with the live schema** — this is the "fresh deploy bootstrap" file and its DDL is 4 months behind reality. Anyone running `pnpm tsx scripts/init-db.ts` on an empty database today would get the wrong poems table (no category col, ENUM dynasty without 汉/清).

## 一、四类错误，以及每类怎么办

代码在 `lib/wechat-types.ts::classifyWechatError`，把微信的 errcode 分成
四个类。**分类决定行为**，这是整个设计里最容易写错的地方。

| 类 | errcode | 行为 | 为什么 |
|---|---|---|---|
| `WechatTokenError` | `40001` | **刷新 token，重试一次**；再失败就停手 | token 过期是可恢复的，重试有意义 |
| `WechatRecipientError` | `43101` | **跳过这个人，继续往下发** | 用户取关/免打扰，跟别人无关 |
| `WechatParamError` | `40003` `40037` `47003` `48001` | **停手，不重试** | 同样的参数必然同样失败，重试只是烧配额 |
| `WechatQuotaError` | `45009` | **停手，等下一天** | 今天的额度用完了，继续打只会一直失败 |

其余错误码走 `WechatApiError`（通用的 500）。

⚠️ **`errcode: 0` 不是「对方收到了」**，只代表微信平台接受并投递。微信对模板
消息**不提供送达回执**，所以数据库里的 `sent` 只说明平台收下了。UI 上写的是
「平台接受」，测试里有一条专门盯着这个词不许变成「已送达」。

### 真机上补的一件事：错误翻译

跑真机时发现一个问题：`/api/admin/wechat/followers` 失败时返回的是
`{"code":"server","message":"server error"}`。管理员看到这句话既分不清是
口令错了还是没配白名单，也没有下一步可做 —— 唯一的合理动作是提 bug 报告，
而实际上每个原因都有已知的修法。

`lib/api-handler.ts` 早就有 `translate` 这个钩子（`lib/webfont/api-schema-error.ts`
是现成的例子），所以按同样的写法加了 `lib/wechat-api-error.ts`：

| 微信错误 | 译成的 code | 管理员看到的 |
|---|---|---|
| `40164` | `wechat_ip_not_whitelisted` | 服务器公网 IP 不在白名单，请到公众号后台加入 |
| `40013` | `wechat_bad_credentials` | AppID 无效，请检查（wx 开头 18 位） |
| `40001` | `wechat_token_invalid` | access_token 失效，请检查 AppID 与 AppSecret 是否匹配 |
| `48001` | `wechat_no_permission` | 接口未授权，公众号后台还没开模板消息权限 |
| `45009` | `wechat_quota_exceeded` | 今日额度用完，请到「接口权限」页看剩余额度 |
| `47003` | `wechat_template_mismatch` | 模板不匹配，请确认模板 ID 与字段名 |
| `43101` | `wechat_recipient_unreachable` | 该用户取关/免打扰，跳过，不影响其他人 |
| 其他 | `wechat_error` | `微信错误 <code>：<微信原话>` |

状态码用 **503**：服务器是好的，微信那边还没准备好，改完重试就行。翻译器
**只认微信错误** —— 别的错误一律返回 `null`，交给通用的 500。一个乱认错误的
翻译器比不翻译更糟，因为它会告诉管理员错的原因。

### 没做到的 —— ⚠️ 这一节才是重点

**消息没有真的发出去。** 原因只有一个：**微信侧的凭据还没有配**。

`app_config` 里 `wechat.app_id` / `wechat.app_secret` 都是空的，`.env` 里也没有。
所以：

- **关注者人数**：拿不到。不是代码问题 —— 请求真的打到了微信，微信真的回包了，
  回的是 `40013 invalid appid`。
- **模板 ID**：没有真的模板，所以用的是占位符 `TM00001`。
- **消息有没有到手机上**：**没人能说它到了**，因为它根本没发出去。

⚠️ **数据库里 `sent` 不等于对方收到了** —— 微信没有送达回执，库里那一行只说明
平台收下了。要确认对方真的收到，**得有人自己看手机**。这一条在真机上没法
自动化，也没法用测试代替。

**所以这个功能目前是「代码与数据链路已验证，微信侧配置未验证」。**
要在真机上跑完最后一公里，需要：

1. 在公众号后台把服务器公网 IP 加进 **IP 白名单**（否则 `40164`）。
2. 在「模板库」申请一个模板，记下**模板 ID** 和**字段名**。
3. 在 `/admin/wechat` 填 AppID / AppSecret，勾上「启用微信公告」。
4. 在 `/admin/scheduler` 确认 **scheduler 本身是开着的**（`scheduler.enabled`
   默认 `'0'` —— **默认关闭**）。`wechat-broadcast-send` 这个任务默认是开的
   （默认 `'1'`），但 scheduler 整体关着的时候，任务开关设成什么都没用。
5. 写一条公告，等 scheduler tick，然后**看手机**。

## 三、微信侧必须配的两件事（代码代劳不了）

1. **服务器公网 IP → IP 白名单**。不加就是 `40164`，100% 失败，而且错误信息
   不会点名白名单，很难查。
2. **模板 ID + 字段名**。字段名必须与模板里的**完全一致**（`keyword1` /
   `thing2` / `first` / `remark`），多一个空格、少一个大小写都会 `47003`。

另外一条是**账号本身**：必须是**认证服务号**（订阅号没有模板消息权限），
而且后台要开模板消息接口权限（否则 `48001`）。

## 四、没做的事

- **群发消息**（`message/mass/send`）—— 用户只要求模板消息。
- **OAuth / 用户授权** —— 服务号已认证，关注者已存在，不需要。
- **关注者表** —— 关注者每次现拉，不落库。拉一次是一次的成本，
  而落库意味着要处理退订同步。
- **逐条收件人日志** —— 微信没有逐人回执，一行记 N 份同样的低信息量事实，
  而且每次广播线性增长。只留四个计数。
- **送达回执** —— 微信不提供，做不出来。
- **退订 / 免打扰的持久化** —— `43101` 是跳过，不是记录。
- **每日额度面板** —— 额度以后台「接口权限」页为准，代码读不到。
- **消息内容的富文本** —— 纯文本，不渲染 HTML。

---

## 五、这个功能最容易踩的坑

1. **`errcode: 0` ≠ 送达。** 表头写「平台接受」，不写「已送达」。
2. **两层开关。** `wechat-broadcast-send` 默认**开**（`'1'`），但 scheduler
   整体默认**关**（`scheduler.enabled` 默认 `'0'`）—— 常见卡住的是后者，
   公告会一直排队不发。
3. **默认间隔是 60 分钟**，不是 1 分钟。
4. **字段名必须完全一致**，否则 `47003`。
5. **参数类错误不重试** —— 重试只是烧配额。
6. **每个 tick 只发一条公告** —— 一次广播要遍历所有关注者，
   同一 tick 发第二条等于白烧一倍配额。
